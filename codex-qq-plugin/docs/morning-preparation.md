# 早报提前准备与定时发送

官方逐群早间天气、三号楼自习简报共用两阶段调度，时区为 Asia/Shanghai：

- `alexbot-group-morning-prepare.timer` 每天07:28调用固定准备接口，只生成已订阅项目，不发QQ、不占发送额度。
- 原 `alexbot-group-morning.timer` 仍每天07:30调用发送接口，复用本日准备结果；某项尚未完成时，另一项可先发送。实际送达仍受QQ上传和既有发送限额影响。
- 两个定时器均不补跑。原07:30–07:45发送窗口和逐群逐图幂等键保持，截止检查覆盖core排队和QQ上传后的消息提交。

定时天气和空气每次HTTP上限45秒，普通查询仍15秒。两个来源各自最多重试一次，只重取超时、连接失败或缺测的来源；总获取预算约105秒，后一次按剩余预算缩短。429、模型时效、单位和元信息错误不放宽。48小时主要天气字段、PM2.5、首日天气类型/风摘要及户外指数完整后才渲染；最终缺数据则记录`MORNING_DATA_INCOMPLETE`并跳过天气图，另一项不受影响。

校园定时采集导航45秒、登录等待60秒、查询45秒，保留210秒worker总上限和单轮不重试。平常导航25秒、登录40秒、查询20秒保持不变。新profile仅由内部定时report调用选择，不进入自然语言工具参数。

准备过程复用现有单一主服务，天气网络和校园采集可以重叠，渲染/浏览器仍经过heavy-work队列。仅缓存当天两个图片；跨天淘汰，进程重启后07:30入口重新生成未完成内容，不能保证重启后仍按秒发出。重复准备/发送共享任务，不重新取数；已有投递账本跨重启去重。准备时捕获订阅版本，关闭后重新开启不复活旧图；07:28之后才新增的订阅下一次准备生效。

控制台状态显示07:28准备、07:30发送及两项准备状态。管理员`/api/morning/preview`使用相同完整性检查和长超时，返回质量和图像字节数，但不发送QQ。`/api/group/morning/prepare`与`/run`只接收空对象；任意收件人、日期和超时参数均拒绝。准备/发送不持有长时间控制台配置锁。

部署与验收回执见根目录HANDOVER最新记录。回退保留最新账本，停用新增prepare.timer，恢复原正式源码与单元；不得启用退役OneBot或旧早报服务。
